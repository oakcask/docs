## 要旨 案

本稿は、ソフトウェアエンジニアリングを「要求を実装する作業」ではなく、「システムをあるべき状態へ導き続ける経験的な設計・制御活動」として捉え直す。中心となる比喩は reconciliation loop である。ここでは reconciliation loop を、あるべき状態と現在状態との差分を観測し、コード、設計、運用、組織プロセスの変更によって差分を小さくし、その結果に基づいて方針自体も更新する反復的な営みと定義する。

この見方は、Scrum の透明性・検査・適応、Kubernetes controller の desired state と current state の調整、自己適応システムの MAPE-K loop、要求工学における要求・仕様・環境仮定の関係、ソフトウェア進化論における E-type system の継続的変化と接続できる。一方で、あるべき状態は最初から完全には定義されない。性能、信頼性、保守性、開発速度、セキュリティ、コスト、説明責任、組織能力などの制約は相互に衝突し、途中で変化する。そのため、方針決定は制約充足問題または多目的最適化問題に似ているが、純粋な数理問題ではなく、プロトタイプ、リリース、計測、障害、ユーザーフィードバックを通じて経験的に解かれる。

さらに本稿は、ソフトウェアエンジニアリングとマネジメントの同型性を論じる。マネジメントもまた、方針を立て、状況を観測し、資源を配分し、制約を調整し、組織をあるべき姿へ導く営みである。ただし、ソフトウェアエンジニアリングには、方針をコード、テスト、CI/CD、Infrastructure as Code、Policy as Code などの実行可能な人工物へ変換し、観測・検証・自動化・再現性を高められるという固有性がある。

結論として、ソフトウェアエンジニアリングとは、システムを reconciliation loop により導き、その方針決定のための制約充足問題を経験的手法で解くことである。
