## 第10章 結論：ソフトウェアエンジニアリングとは、経験的な制御と設計の技術である

本稿では、ソフトウェアエンジニアリングを「要求をコードへ翻訳する活動」としてではなく、「システムを望ましい状態へ導き続ける活動」として捉えてきた。この見方に立つと、コードを書くことは重要でありながら、全体の一部である。より本質的なのは、変化する現実の中で、何を望ましい状態と見なし、どの差分を閉じ、どの制約を受け入れ、どの制約を変えるかを決め続けることである。

ソフトウェアは、完成して終わる人工物ではない。特に、現実世界の業務、利用者、市場、制度、技術基盤と相互作用するシステムは、環境の変化から自由ではいられない。Lehman が E-type system について論じたように、現実に埋め込まれたソフトウェアは、変化し続けなければ有用性を失っていく（Lehman, 1996）。Parnas が指摘した software aging も、変更の蓄積や環境変化によってソフトウェアが劣化するという事実を思い出させる（Parnas, 1994）。したがって、ソフトウェアエンジニアリングは、一度正しいものを作る技術というより、変化に応答しながら正しさを保ち直す技術である。

その応答の基本構造が reconciliation loop である。望ましい状態を仮に置き、現在状態を観測し、差分を解釈し、変更を加え、結果を再び観測する。この構造は、Kubernetes controller のような技術的な制御ループにも、自己適応システムの MAPE-K loop にも見られる。MAPE-K loop は、Monitor、Analyze、Plan、Execute over Knowledge の略であり、知識基盤の上で監視、分析、計画、実行を回す自己管理システムの枠組みである（Kephart & Chess, 2003）。ソフトウェアエンジニアリングもまた、観測と変更を通じて差分を閉じ続ける点で、経験的な制御の営みである。

ただし、ソフトウェアエンジニアリングを単純な制御問題として扱うことはできない。なぜなら、望ましい状態そのものが最初から完全には分からないからである。要求は、実装前にすべて列挙できる項目ではない。Zave と Jackson が示したように、要求、仕様、環境仮定は相互に関係しており、仕様は環境の中で要求を満たすために定められる（Zave & Jackson, 1997）。さらに実務では、要求を満たす仕様を考えるだけでなく、何を要求として扱うべきかも、実装、観測、対話を通じて更新される。

この点で、設計は問題を解いてから作る活動ではなく、作りながら問題を理解する活動である。Rittel と Webber が wicked problem と呼んだような問題では、問題の定義と解決案は切り離しにくい（Rittel & Webber, 1973）。この概念は社会計画の文脈から来ているため、ソフトウェア開発全般へ無限定に広げるべきではないが、探索的なプロダクト開発や業務プロセスを含むシステム開発では同様の性質が現れうる（Yeh, 1991）。Dorst と Cross は、問題空間と解決空間が共進化する設計過程を論じた（Dorst & Cross, 2001）。Ralph の Sensemaking-Coevolution-Implementation theory も、ソフトウェア設計において意味づけ、問題と解の共進化、実装が絡み合うことを示している（Ralph, 2015）。このため、reconciliation loop は現在状態を望ましい状態へ近づけるだけでなく、望ましい状態そのものを学習し、更新するループでもある。

方針決定は、この学習ループの中で行われる。そこでは、性能、信頼性、保守性、開発速度、セキュリティ、コスト、説明責任、ユーザー体験、組織能力など、多数の制約が同時に現れる。Search-Based Software Engineering は、ソフトウェア工学上の問題を探索や最適化の問題として扱う研究領域であり、Harman と Jones がその考え方を明確に提示した（Harman & Jones, 2001）。その後、この領域は要求、プロジェクト計画、テスト、保守、再工学などへ広がってきた（Harman, Mansouri, & Zhang, 2012）。この観点は、ソフトウェアエンジニアリングが複数の候補からよりよい構成を探す活動であることをよく示している。

ただし、本稿が主比喩として置くのは、多目的最適化よりも制約充足的な見方である。多目的最適化は、品質、速度、コスト、保守性などの目的を同時に改善する見取り図として有効である。しかし、実務の判断では、予算、人員、期限、既存システム、法規制、運用能力のような有限な条件が先に境界を作る。したがって問題は、理想的な評価関数を最大化することよりも、破綻しない実行可能解を見つけ、現実から学びながら制約そのものを更新することとして現れる。ときには、制約だと思っていたものを制約集合から外すことも、この活動に含まれる。

一方で、実務上の方針決定は、完全に形式化された探索問題ではない。制約は曖昧で、途中で変わり、関係者によって重みづけが異なる。したがって、ここでいう制約充足は、最初から与えられた条件を機械的に解くことではない。むしろ、制約を発見し、衝突を明らかにし、受け入れ可能な妥協点を見つけ、その結果を実装と運用で検証する活動である。さらに、観測と対話を通じて、ある条件が本当に制約なのか、それとも変更可能な前提なのかを見直す活動でもある。経験的手法とは、厳密さを捨てることではなく、不完全な情報のもとで観測可能な現実に学ぶ態度である。

この構造は、Scrum にも表れている。Scrum は、透明性、検査、適応に基づく経験的なプロセス制御として説明される（Schwaber & Sutherland, 2020）。Product Goal と Sprint Goal は望ましい将来状態や短期目標を暫定的に表現し、Product Backlog はそこへ向かうための仮説や作業を透明化して順序づける。Sprint Review や Retrospective は現在状態を観測して次の変更を決める場になる。Scrum を会議体の集合として見ると本質を見失いやすい。本稿の比喩でいえば、Scrum は組織がプロダクトを導くための reconciliation loop として読むこともできる。

さらに、ソフトウェアエンジニアリングはマネジメントとも同型性を持つ。マネジメントもまた、方針を立て、状況を観測し、資源を配分し、制約を調整し、組織を望ましい状態へ導く活動である。Beer の管理サイバネティクスや Viable System Model は、組織を環境変化に適応し続ける自己制御システムとして捉える視点を提供する（Beer, 1972; Beer, 1985）。ソフトウェアプロダクト、開発組織、運用体制は、いずれも目的を持つ社会技術システムとして捉えられ、そこでは技術的判断と組織的判断が分離しにくい（Baxter & Sommerville, 2011）。また、Conway が論じたように、組織のコミュニケーション構造はシステム設計に反映されやすい（Conway, 1968）。

ただし、ソフトウェアエンジニアリングには固有性もある。ソフトウェアでは、方針をコード、テスト、継続的インテグレーションと継続的デリバリー、Infrastructure as Code、Policy as Code などの実行可能な人工物へ変換できる。継続的インテグレーションと継続的デリバリーは、変更を継続的に統合し、検証し、リリース可能な状態へ近づける実践である。Infrastructure as Code はインフラ構成をコードとして管理する実践であり、Policy as Code はポリシーを機械で検証または適用可能な形で表現する実践である。Open Policy Agent はその具体例として、ポリシーをコードとして指定し、Kubernetes、継続的インテグレーションと継続的デリバリーのパイプライン、API gateway などへ適用できる汎用ポリシーエンジンである（Amazon Web Services, n.d.; Open Policy Agent, n.d.-a; Open Policy Agent, n.d.-b）。これにより、少なくともインフラ構成やアクセス制御のように機械で扱える領域では、観測、検証、自動化、再現性を強く持たせられる。

制度や組織をソフトウェア的に見ることも、この延長にある。Lessig が「Code is Law」と述べたように、コードやアーキテクチャは人の行動を規制する力を持つ（Lessig, 2000）。アクセス制御、デプロイ権限、CI/CD の検査、監査ログのようにソフトウェアへ埋め込まれた制度は、人間の行動を制約する実行可能なルールとして振る舞う。一方、承認フローや評価制度のように人間の解釈と運用に強く依存する制度は、同じ比喩で読めるとしても、コード化されたルールと同列には扱えない。人間を含む制度は、Kubernetes controller のように単純には reconcile できない。そこには解釈、納得、権力、感情、抵抗、学習がある。この限界を忘れると、ソフトウェア的な見方は有効な分析道具ではなく、粗雑な統制の発想になってしまう。

ここまでの議論は、エンジニアの育成と評価にもつながる。AI がコード生成を日常的に支援する現在、限定された実装タスクでは AI 支援が完了時間を短縮しうることが報告されている（Peng et al., 2023）。一方で、AI 利用が組織全体のソフトウェアデリバリ性能へ与える影響は一様ではない。DORA 2024 はデリバリ安定性とスループットへの負の関連を報告し、DORA 2025 と 2026 年の記事は、AI が組織能力を増幅し、スループット改善と不安定性増加を同時にもたらしうると整理している（DORA, 2024; DORA, 2025; DORA, 2026）。実装案を生成し、試すコストが下がるほど、どの案を採るか、どの制約を優先するか、どのリスクを観測可能にしてから進むかという判断が重要になる。この判断能力は、才能だけに属するものではない。Dreyfus と Dreyfus の技能獲得モデルが示すように、学習者は規則に依存する段階から、状況をより全体的に捉える段階へ進む（Dreyfus & Dreyfus, 1980）。Schön の反省的実践が示すように、専門家は行為の中で状況を読み替え、試し、反省しながら問題を形成する（Schön, 1983）。

したがって、エンジニアの成長に必要なのは、単に難しい実装を任されることではない。判断の材料、制約、仮定、代替案、事後の結果を言語化する場が必要である。設計レビュー、障害対応のふりかえり、技術選定、リリース判定は、認知的徒弟制の場として設計できる。熟練者は結論だけを渡すのではなく、何を見て、何を捨て、どの条件なら判断を変えるのかを示す。学習者は、小さく本物の判断に参加し、結果から学ぶ。

評価も、コード量や短期成果だけに閉じてはならない。よい判断は、しばしば「起こらなかった障害」や「手戻りや作り直しを発生させなかった設計」のように、回避された損失として現れる。結果だけでは、よい判断と偶然を区別しにくい。Miller の評価ピラミッドが知識、能力、実演、実践を区別したように、エンジニアの意思決定も、知っているかだけでなく、説明できるか、やってみせられるか、実際のプロジェクトで継続的に行えるかを見なければならない（Miller, 1990）。この評価は、個人を監視するためではなく、組織が価値ある判断を学習可能な技能として扱うためにある。

以上を踏まえると、本稿の中心命題は次のようにまとめられる。ソフトウェアエンジニアリングとは、システムを reconciliation loop により導き、その方針決定を制約充足的な探索として経験的に進めることである。

この定義は、コードを書くことの価値を小さく見積もるものではない。むしろ、コードを書くことを、より大きな営みの中に正しく位置づけるものである。コードは、方針を現実に作用させる強力な媒体である。テストは、方針と実装のずれを観測する装置である。運用は、システムと環境の関係を学ぶ場である。設計は、制約の衝突を扱い、次に閉じるべき差分を選ぶ判断である。

したがって、よいソフトウェアエンジニアリングとは、最初から正解を知っているかのように振る舞うことではない。望ましい状態を暫定的に置き、観測によって現実を知り、制約を明らかにし、変更を通じて学び、必要であれば方針そのものを更新することである。そして、その判断過程を他者が学べる形にすることである。変化する現実の中で、システムをどこへ導くのかを問い続けること。それが、ソフトウェアエンジニアリングの中心にある。
