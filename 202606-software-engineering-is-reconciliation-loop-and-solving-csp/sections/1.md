## 第1章 導く営みとしてのソフトウェアエンジニアリング

ソフトウェアエンジニアリングは、しばしば「要求を聞き、設計し、コードを書き、テストして届ける活動」と説明される。この説明は間違っていない。しかし、実務の感覚からすると、少し静的すぎる。私たちが日々向き合っているのは、最初から輪郭のはっきりした要求でも、完成すれば安定して価値を出し続ける成果物でもない。利用者の期待は変わり、市場や法制度は変わり、技術基盤も組織の能力も変わる。そのたびに、昨日まで妥当だった設計や運用が、今日の現実から少しずつずれていく。

本稿では、ソフトウェアエンジニアリングを「システムを望ましい状態へ導き続ける営み」として捉え直す。ここでいうシステムには、コードだけでなく、利用者、運用、開発組織、意思決定のプロセス、制度的な制約も含まれる。ソフトウェアの価値は、コード単体の内部に閉じて存在するのではなく、それが置かれた環境との関係の中で立ち上がる。したがって、環境が変われば、同じコードであっても望ましい状態から外れうる。

この捉え方は、AI が日常的にコード生成を支援する時代にいっそう重要になる。GitHub Copilot を用いた制御実験では、JavaScript の HTTP server を実装する局所的なタスクにおいて、AI 支援を受けた処理群が対照群より短時間で完了したことが報告されている（Peng et al., 2023）。一方で DORA 2024 は、AI 利用が個人の生産性、フロー、仕事満足度には正の関連を示しつつ、ソフトウェアデリバリの安定性やスループットには負の関連を示したと報告している（DORA, 2024）。さらに DORA 2025 は、AI の主な役割を、組織の既存の強みと弱みを増幅することだと整理した（DORA, 2025）。DORA の 2026 年記事も、AI が初期のコード生成を加速しうる一方で、検証負荷を増やし、スループット改善とデリバリ不安定性の増加が同時に起こりうると述べている（DORA, 2026）。したがって、ここで重要なのは「コード生産が一般に速くなる」と断定することではない。むしろ、実装案を生成し、試すコストが下がりうるほど、どの問題を解くべきか、どの制約を優先すべきか、どの変更を今は避けるべきか、どのリスクを観測可能にしてから進むべきか、といった判断がシステム全体の成否を左右しやすくなる。

優れたエンジニアは、この種の判断を日常的に行っている。たとえば、短期的なリリース速度と長期的な保守性を秤にかける。障害対応の速さと原因分析の深さを調整する。新しい技術を導入する魅力と、チームの学習コストや運用負荷を比べる。ところが、こうした判断は周囲から見えにくい。なぜなら、よい判断の成果は、しばしば「起こらなかった障害」「増えなかった複雑性」「スムーズに進んだ移行」として現れるからである。つまり、成果が直接の増分ではなく、損失の回避やリスクの未然抑制として現れることがある。

この見方の中心に置くのが、reconciliation loop である。reconciliation loop とは、望ましい状態と現在状態との差分を観測し、その差分を小さくするようにシステムを変更し、変更の結果を再び観測する反復的な営みを指す[^reconciliation]。この言葉は Kubernetes の controller における desired state と current state の調整を想起させる。Kubernetes の controller は、望ましい状態と現在状態を比較し、現在状態を望ましい状態へ近づける制御ループとして説明される（Kubernetes Documentation, n.d.）。本稿では、この構造を特定技術に閉じたものではなく、ソフトウェアエンジニアリング全体を理解するための比喩として用いる。

ただし、この比喩にはすぐに難しさが現れる。もし「望ましい状態」が最初から完全に分かっているなら、エンジニアリングはその状態へ到達するための実装問題にかなり近づく。けれども実務では、望ましい状態そのものが曖昧で、暫定的で、しばしば関係者の間で一致していない。性能を上げればコストが増えるかもしれない。開発速度を上げれば保守性が下がるかもしれない。セキュリティを強めればユーザー体験が悪化するかもしれない。どの制約を満たし、どの制約を緩め、どの制約を後回しにするかは、最初から機械的に決められない。

この意味で、ソフトウェアエンジニアリングにおける方針決定は、制約充足問題に似ている。制約充足問題とは、与えられた複数の制約を同時に満たす値や構成を探す問題である。複数の目的を同時に改善する多目的最適化問題という見方もできるが、実務では、よりよい指標を追う前に、有限な予算、人員、期限、既存システム、法規制、運用能力といった条件を満たさなければならない。ただし、実務上の方針決定は、純粋な数理問題ではない。制約は途中で発見され、重みづけは議論によって変わり、環境そのものも動き続ける。さらに、制約だと思われていたものが、観測を通じて変更可能な前提や単なる慣習だったと分かることもある。そのため、ここで必要になるのは、最初に完全な答えを出す能力ではなく、プロトタイプ、リリース、計測、障害対応、ユーザーフィードバックを通じて、制約と解を同時に育てていく能力である。

この見方は、複数の既存研究と接続できる。Lehman は、現実世界に埋め込まれた E-type system が継続的に変化しなければ有用性を失うことを論じた（Lehman, 1996）。Zave と Jackson は、要求、仕様、環境仮定の関係を整理し、要求が単なる実装項目ではなく環境における望ましい条件であることを示した（Zave & Jackson, 1997）。また、Scrum は透明性、検査、適応に基づく経験的なプロセス制御として説明される（Schwaber & Sutherland, 2020）。これらはそれぞれ異なる文脈の議論だが、いずれも「最初に完全な計画を作って直線的に進む」というより、「観測し、解釈し、適応する」という構造を持っている。

本稿の問いは、次の四つである。第一に、ソフトウェアを変化する環境に適応し続けるものとして捉えるなら、エンジニアリングの中心は「完成」ではなく何になるのか。第二に、方針や要求が最初から明確ではないことを前提に、それらを実装と観測を通じてどのように形成し、扱っていくのか。第三に、方針決定は単なる意思決定なのか、それとも複数の制約を同時に満たそうとする経験的な制約充足的探索なのか。第四に、その判断能力は才能なのか、それとも教育と実践によって育てられる技能なのか。

以降では、まずソフトウェアが変化する環境の中で進化し続けるシステムであることを前提として、その前提を採用するとエンジニアリングの捉え方がどう変わるかを確認する。次に、reconciliation loop を、望ましい状態と現在状態の差分を閉じる構造として定義する。そのうえで、望ましい状態が最初から明確ではないこと、方針決定が複数制約の調整であること、Scrum やマネジメントとの同型性を論じる。さらに、組織や制度をソフトウェア的に見ることの有効性と限界を扱い、最後に意思決定能力を技能として育てる方法と評価する方法を検討する。

本稿の中心命題は、次のとおりである。ソフトウェアエンジニアリングとは、システムを reconciliation loop により導き、その方針決定を制約充足的な探索として経験的に進めることである。

[^reconciliation]: reconciliation は、差異や不一致を調停し、整合させることを意味する。本稿では、望ましい状態と現在状態の差分を継続的に扱う活動を指す比喩として用いる。
