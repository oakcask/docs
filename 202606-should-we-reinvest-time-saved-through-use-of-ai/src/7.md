## 第7章　Cognitive Kanban の提案：ルールと実践

この章では、第6章の分類を使って、実践モデルとして Cognitive Kanban を提案する。Cognitive Kanban とは、AIエージェント運用において、人間のワーキングメモリ、レビュー容量、状況認識、チーム対応余力、回復可能性を守るためのカンバン型運用である。訳語としては「認知カンバン」も考えられるが、初出では Cognitive Kanban、認知カンバンと併記する。

この章の役割は、理論的分類をルールと実践へ変換することである。State、Mode、Slot、Risk、Externalization を見ながら、人間が監督できる量だけを流す。

カンバン列:

```text
Backlog
Framing
Agent Running
Review Needed
Human Integrating
Done
```

Mode別のWIP上限案。Batch、Checkpoint、Interactive は列ではなく、Agent Running 内のMode別上限として扱う。

```text
Framing: 1
Agent Running: 2から3
  Batch: 2から3
  Checkpoint: 1から2
  Interactive: 0から1
Review Needed: 1から2
Human Integrating: 1
Done: 無制限
```

ここでの数値は研究で検証された閾値ではない。ワーキングメモリ容量、注意残留、レビュー待ちの詰まりを踏まえ、初期運用で破綻しにくくするための保守的な仮置きである。レビュー待ち時間、手戻り、レビュー漏れ、割り込み後の復帰しやすさを見ながら調整する。

基本ルール:

```text
Rule 1:
Framing なしに重い作業を流さない。
少なくとも Goal、Box、Check を書く。
Slot 2 以上、または Risk が高い作業では、成功条件、止める条件、レビュー観点も明確にする。

Rule 2:
重い実装エージェントは、安全側のデフォルトとして同時に1本まで。
Slot 3、または Risk が高い作業を重い実装エージェントとして扱う。
外部化が十分で、変更範囲が独立し、レビュー容量が確保できる場合のみ2本目を許容する。

Rule 3:
Agent Running より Review Needed のWIPを優先して減らす。
Review Needed が2以上になったら、新規エージェントを起動しない。

Rule 4:
Interactive な Agent Running は、人間自身の作業WIPとしても数える。
AIが実行している時間があっても、人間が質問に答え、判断し、次の一手を選び続けるため、休憩や空き時間として扱わない。

Rule 5:
人間の設計判断タスクと重いエージェント監督を同時に増やさない。
記憶負荷を外部化できても、判断、レビュー、統合の負荷は残る。

Rule 6:
エージェント待ち時間は、まず外部化、レビュー、休憩に使う。
それでも余裕がある場合だけ、新規投入する。

Rule 7:
常に1スロットを割り込み、チーム会話、異常検知用に空けることを試す。

Rule 8:
先に独立性の高い Batch タスクをエージェントへ投入し、残った前景注意で Interactive な判断やチーム対応を行う。
ただし、Review Needed が増えたら Interactive よりレビュー待ちの解消を優先する。

Rule 9:
休憩は時刻だけでなく、認知スロットの枯渇兆候で入れる。

Rule 10:
WIP上限は固定せず、観察で調整する。
```

Rule 10 は、Cognitive Kanban を運用ルールではなく改善ループとして扱うためのルールである。State、Mode、Slot、Risk、Externalization は初期値だけでは安定しない。AIエージェントの能力、チームのレビュー慣行、扱うコードベース、障害対応の頻度、チーム内の応答期待によって、同じ本数でも人間側の負荷は変わる。したがって、計測とツールのアシストが重要になる。

計測は、単純な生産量最大化ではなく、人間の監督性能を守るために使う。SPACE の考え方に沿えば、Activity、すなわちコミット数や実行本数のような活動量だけを見るのでは不十分である。Satisfaction and well-being、Performance、Communication and collaboration、Efficiency and flow も合わせて見る必要がある。Developer Experience の観点でも、開発者の摩擦、待ち時間、フィードバックの質、認知負荷を含めて改善対象にする。

ツールで支援したい運用:

- WIP上限を超えそうなときに警告する。
- Review Needed が滞留しているときに、新規投入よりレビューを促す。
- Checkpoint が近い状態で Interactive な集中作業へ入ろうとしたときに注意を出す。
- Slot 3 または Risk 高の作業が複数並んだときに、同時実行の見直しを促す。
- Goal、Box、Check、Stop、Resume の未記入を検出する。
- レビュー待ち時間、復帰時間、差し戻し、レビュー漏れ、不要な再作業を集計する。
- 自動ログだけでなく、短い自己報告や振り返りコメントを残せるようにする。

このとき、ダッシュボードは人間を採点するためのものにしない。自動計測された活動量と自己報告された生産性はずれることがあるため、ログは対話の材料として使う。たとえば、Agent Running が多いのに本人の負荷感が低く、Review Needed も溜まっていないなら Batch を少し増やせるかもしれない。逆に、実行本数が少なくても、復帰時間や差し戻しが増え、本人が状態を思い出しにくいなら、WIP上限を下げるべきである。

Interactive な作業のミニカード:

```text
Goal: この集中セッションで決めること
Stop: どこで止めるか
Resume: 中断後に最初に見るもの
```

集中が必要なタスクには、カンバンではなく集中セッションとしての扱いを与える。開始時に Goal、Stop、Resume だけを書く。作業中は状態更新をしない。中断が入った場合だけ Resume を更新する。終了時に、次がレビューなのか、継続なのか、完了なのかをカンバンへ戻す。この方法は、カンバンを「常時操作する管理画面」ではなく、「投入前と復帰時に使う外部記憶」として位置づける。

Checkpoint の扱い:

Checkpoint は、Batch のように先にエンキューできるが、完全に放置できるわけではない。確認条件、確認予定、判断事項が明確なタスクであり、人間のスロットを「常時」ではなく「節目」で消費する。したがって、Batch を仕込んだ後に Interactive な作業へ入る場合、近い Checkpoint がないかを確認する。近い Checkpoint があるなら、先に確認を済ませるか、Interactive の Stop をその確認時点に合わせる。

この細分化の実務上の価値は、将来の中断予約を見える化する点にある。Batch は、現在も近い未来も人間の注意をあまり予約しない。Checkpoint は、現在は軽いが、近い未来に判断を要求する。したがって、Batch と Checkpoint を分けることで、空いた時間を Interactive な集中作業に使ってよいのか、それとも短いチーム対応、レビュー準備、軽い整理にとどめるべきなのかを決めやすくなる。

休憩の発火条件:

```text
- Review Needed が溜まっているが、レビュー品質が落ちている。
- 同じログや差分を何度も見ている。
- エージェントの状態を即座に思い出せない。
- チャット割り込み後、元タスクに戻るのが重い。
- 新しいエージェントを起動したくなったが、目的が曖昧である。
```

観察して調整する指標:

- レビュー待ち時間。
- 差し戻し。
- レビュー漏れ。
- 割り込み後の復帰時間。
- 説明に詰まった回数。
- 不要な再作業。
- Checkpoint の予定超過。
- Slot 3 または Risk 高の同時滞留。
- Goal、Box、Check、Stop、Resume の未記入率。
- 短い自己報告による負荷感、集中しやすさ、復帰しやすさ。

この章の核心:

- Cognitive Kanban は、生産性を下げるための制約ではない。
- レビュー漏れ、設計逸脱、不要な再作業、チーム同期不全を防ぐための制御である。
- 外部化によって上限は少し押し上げられるが、判断とレビューのボトルネックは残る。
- 計測とツール支援は、活動量を増やすためではなく、人間が監督できる状態を保つために使う。
- ログだけで判断せず、開発者本人の主観的負荷やチームの文脈と合わせて調整する。
- AIを抑え込むことではなく、AIを継続的に使える範囲へ流量を整えることが目的である。
