## 第6章　監督負荷を分類する：WIP制限と外部化のための判定軸

この章では、認知スロット管理を実務ルールへ落とす前段として、AIエージェント作業の監督負荷を分類する。6章の役割は、具体的なルールを列挙することではなく、5章までの議論を使って「何を重い作業として扱うのか」を判定する理論的な枠組みを作ることである。

分類の前提:

- 分類対象は、タスクそのものではなく、人間が戻って判断すべき未完了文脈である。
- 所要時間、エージェント本数、生成物の量だけでは、人間側の負荷は測れない。
- 短時間の作業でも、設計判断や承認責任が重ければ認知スロットを大きく使う。
- 長時間走る処理でも、成功条件と確認方法が明確であれば監督負荷は小さくできる。
- 第2章のワーキングメモリ・注意残留・レビュー容量、第3章の回復可能性、第4章の out-of-the-loop と過信、第5章の流量制御を、実務上の判定軸に変換する。

提案する分類軸は、State、Mode、Slot、Risk、Externalization の5つ。

State:

```text
Backlog
Framing
Agent Running
Review Needed
Human Integrating
Done
```

State は現在の監督フェーズを表す。これは単なるカンバン列ではなく、人間の負荷がどこで発生するかを見るための分類である。

- Backlog: まだ着手しない候補。
- Framing: 目的、範囲、禁止事項、成功条件、確認方法を明確にする段階。
- Agent Running: エージェントが実行している状態。
- Review Needed: 人間のレビューを待っている状態。
- Human Integrating: 人間が差分を統合し、必要なら説明や反映を行う状態。
- Done: 監督と統合が終わった状態。

Mode:

Agent Running は単純な待ち時間ではない。実行中の監督負荷を、次の3種類に分ける。

- Batch: 一定時間放置できる実行。成功条件と確認方法が明確で、途中判断をほとんど要しない。
- Checkpoint: 節目で確認する実行。差分拡大、方針変更、テスト失敗、調査結果の分岐などで人間の判断が必要になる。
- Interactive: 人間とAIが短い往復で進める実行。AIが処理している時間があっても、人間は質問に答え、判断し、次の一手を選び続ける。

Mode は、作業中に頻繁に更新するものではなく、Framing 時点で付ける静的なラベルとして扱う。目的は、空いた時間を深い集中に使ってよいのか、近い将来の中断に備えるべきかを見積もることである。

Slot:

Slot は工数ではなく、人間の監督容量をどれだけ占有するかを示す運用上の目安である。エージェント1本を機械的に1スロットと数えない。

- Slot 1: 手離れがよく、結果だけを確認すればよい作業。
- Slot 2: 方針や差分を確認する必要がある作業。
- Slot 3: 設計判断、影響範囲、人間によるレビュー、統合判断が重い作業。

この数値は能力評価ではない。レビュー滞留、手戻り、レビュー漏れ、割り込み後の復帰時間を観察するための仮置きである。

Risk:

Risk は失敗時の影響の大きさである。失敗しても破棄できる調査メモと、本番影響のある認証変更では、同じSlotとして扱うべきではない。Risk が高い作業では、外部化が整っていても、監督イベントを厚くし、WIP上限を低くする。

Externalization:

Externalization は外部化の強さである。外部化とは、人間が頭の中だけで保持している目的、制約、レビュー観点、状態、次に見るべき点などを、カード、チェックリスト、ログ、プロンプト、TODO、ADRなどの外部表象へ移すことである。

ただし、外部化は判断責任を代替しない。外部化できるのは、情報の保持や復帰点の明確化である。設計判断、影響範囲の解釈、複数差分の統合、異常時の介入、最終承認の責任は人間に残る。

この外部化は、個人の手元メモだけで完結させない。提案する分類軸は複雑であり、人間が常に頭の中だけで State、Mode、Slot、Risk、Externalization を正しく更新し続ける前提を置くと、運用そのものが新しい負荷になる。そのため、実務では計測とツール支援を外部化の一部として扱う。

ツール支援で見える化したいもの:

- 現在の State、Mode、Slot、Risk。
- Review Needed の滞留数と滞留時間。
- Checkpoint の予定時刻または確認条件。
- 人間が戻るときに最初に見る Check または Resume。
- 差分量、テスト結果、CI結果、直近ログなどの事実情報。
- 手戻り、差し戻し、レビュー漏れ、不要な再作業の発生。

ただし、ツールが自動取得できるログだけで監督負荷を推定しない。自動計測された活動量と、開発者本人が感じる生産性や負荷は一致しないことがある。したがって、計測は「人間の状態を決めつける」ためではなく、「観察し、対話し、WIP上限や分類を調整する」ために使う。

この位置づけは、SPACE、すなわち Satisfaction and well-being、Performance、Activity、Communication and collaboration、Efficiency and flow を組み合わせて開発者生産性を見る枠組みと相性がよい。また Developer Experience、すなわち開発者が日々の開発活動で経験する摩擦や認知負荷、フロー、フィードバックの質を重視する考え方とも整合する。

外部化の3層:

- 手書きミニカード: 人間が手で書く最低限の情報。
- 詳細カード: ツールが生成・更新する構造化情報。
- 実行ログ: エージェントやCIが自動で蓄積する事実情報。

手書きミニカードの3行フォーマット:

```text
Goal: 何を終えたいか
Box: 触ってよい範囲・禁止範囲
Check: 人間が戻った時に見るもの
```

特に重要なのは Check である。Check は「作業結果を見る」だけではなく、中断後に最初に何を見れば状況を再構成できるかを示す復帰点である。この復帰点がないと、外部化は単なる記録になり、回復可能性を支えない。

この章のキーフレーズ:

- 分類の対象は、タスクではなく未完了文脈である。
- Agent Running は待ち時間ではなく、Batch、Checkpoint、Interactive に分けて監督負荷を読む。
- Slot は工数ではなく、人間の監督容量の占有度である。
- Risk が高い作業では、外部化があってもWIP上限を低くする。
- 外部化は判断責任を代替せず、復帰点を明確にする。
- 複雑な分類は、人間の記憶だけに頼らず、ツールで状態、滞留、復帰点、事実ログを見える化する。
- 自動計測だけで負荷を断定せず、開発者本人のフィードバックと組み合わせる。
- 忘れられるように書くが、忘れてよい量しか流さない。
